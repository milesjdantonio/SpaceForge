# TerraSim repository guidance

TerraSim was renamed from SpaceForge; the local directory and Go module may still
use SpaceForge. See [docs/product.md](docs/product.md) for product context,
[docs/running-locally.md](docs/running-locally.md) for the implemented Go backend, and
[docs/storage-service-api.md](docs/storage-service-api.md) for its routes.

## Implemented backend on this branch

- One Go API handles Firebase authentication and private building JSON storage in
  PostgreSQL. This replaces the earlier proposal for Go accounts plus a Python API.
- The frontend renders buildings. The Go backend stores named JSONB documents with
  owner IDs and timestamps and exposes authenticated create/list/get/replace/delete.
- Building access is scoped to the verified user's local ID in every SQL query.
  Client identity/role fields and legacy role columns must not grant access.
- Entry points are cmd/api and cmd/migrate. The API owns account-authorized design
  tasks, SQL leases/recovery, private projects and atomic generated-building saves.
  Prediction, publishing, inquiry and admin-role APIs remain unimplemented.
- Keep applied migrations immutable and preserve existing data. Legacy tables and
  the unused role column stay for compatibility with existing databases.
- Emulator mode is local development/test only, with a demo- project and loopback
  addresses. Production must reject it. Never add authentication bypasses.

## Frontend and product decisions from main

- Plain HTML/CSS/JavaScript, MapLibre GL JS, three.js, and Rive. Do not introduce a
  framework by assumption. The frontend lives in website/ and runs with npm start.
- The interface is map-first: globe navigation, site outlining, a brief form, a
  building on the lot, a details panel, and a separate full-screen walkthrough.
- MapLibre uses OpenFreeMap vector tiles/buildings and Esri satellite imagery with
  attribution. Production map-data/search providers remain an open choice.
- Solid dark panels with amber actions; do not restore the discarded blueprint look.
- Design computation belongs to the private Gemma/design worker. The frontend sends
  requests to the authenticated API and renders server-persisted results. The contracts are in contracts/;
  start at contracts/FIELDS.md. Do not add local model serving or guess model IDs.
- Status, decisions and what's left: UPDATE.md.
- The design-service/ Go module runs that design service on loopback port 8000 with
  -serve. It reads GEMINI_API_KEY or a gitignored APIKey.txt and requires a server-only
  GENERATION_SERVICE_TOKEN. POST /internal/generate streams progress/results to the
  account API. Server mode has no local queue, result files or provider reply logs.
- With no design service configured, sending shows a clear not-connected state.
  Exactly one labelled sample house lives in website/fixtures/mock-house/.
- Rive assets are generated by website/tools/rive/. Editor-made replacements must
  keep the existing state-machine/input names. Playwright checks use one browser
  at a time. Design/review tooling is described in docs/resources.md.
- There is no catalog, no listings and no inquiries (decided 2026-10-24): every design
  is private; Share packs the building into a link (lib/share.js, #b=...) or a file,
  and the Share panel keeps the links made. Don't add publishing or inquiry
  features back without the user asking.
- The frontend supports metric/imperial units and USD prices.

## Integration boundaries

- The frontend uses storageBaseUrl for generation, projects and building persistence.
  Never send Firebase tokens to the worker or a URL supplied through ?api=. Query
  overrides/provider discovery are removed. Only the API knows the service token.
- Keep design_tasks leases fenced and building/task completion atomic. Recovery may
  recompute a provider request but cannot commit duplicate buildings. Projects use
  composite owner foreign keys; their land is shared metadata and design documents
  remain snapshots. Preserve applied migrations and existing building IDs/documents.
- Frontend lifecycle coordination belongs in controllers/: storage, scene, account
  transitions, generation observation, library and building interaction. main.js wires
  the map and panels to those controllers.
- The frontend supports email/password signup, login, logout, and tab-session
  restoration. Local loopback hosts use the Auth emulator; production needs its
  real Firebase public web API key and HTTPS storage URL in website/js/config.js.
- Generation requires sign-in and the server automatically saves Gemma results, even
  without an open browser. Imported designs and
  previews have a Save building action. My Builds lists private SQL records and
  supports reopen/delete. Account changes clear private render state and caches.
- Session restoration automatically loads every page of the account's saved houses
  and renders all of them. The browser remembers the last selected SQL UUID and
  camera per account. Selection preserves other saved models; sign-out clears every
  private model and cancels stale restoration callbacks. Shared links keep priority.
- Moving or turning a saved building (Done in move mode) automatically persists its
  actual map placement beside the original design. Saves run in order per building, survive selection changes, and reuse the SQL
  UUID, including moves during initial creation. Unsaved imports/previews require
  Save building; failed position saves offer Save changes to retry.
- Building interaction picks rendered 3D geometry before falling back to ground
  footprints. Keep pitched roof/wall dragging separate from map panning, release
  controls on mouseup outside the canvas and touch cancellation, and preserve
  normal empty-land pan and multi-touch gestures.
- Clicking/tapping a building selects it in orange and shows a Move button beside
  it (map/mover.js). Move opens a ground ring with a turn grip (any angle) and a
  grip above the roof; the building can also be dragged by its roof. It may go past
  its land while moving (the outline turns red) but Done only keeps spots inside;
  Escape restores it. Outside move mode, a drag on a building pans the map.
  Empty-land clicks deselect. Keep visual selection separate from the displayed
  document and do not mutate the original design palette when highlighting. First
  selection keeps the details panel closed so it cannot cover the house on mobile.
- Preserve the existing contracts and renderer. Building storage accepts a flexible
  JSON object without imposing a new scene schema. The frontend stores an envelope
  with the original design, estimate, site/brief and actual preview placement; its
  SQL UUID stays separate from the Gemma design ID.
- Production Firebase configuration, generation-provider access, pricing sources,
  notification delivery, and publishing policy need further
  implementation or decisions. Do not silently reintroduce the retired backend plan.

## Working conventions

- Leave README.md unchanged unless explicitly requested; backend instructions belong
  in docs/running-locally.md. Preserve upstream documentation when merging main.
- Keep credentials, ID tokens, and building documents out of logs/version control.
  Do not invent credentials, models, pricing data, or provider configuration.
- Run go vet and go test -race from storage-service/. Set TEST_DATABASE_URL to a dedicated
  PostgreSQL/PostGIS database to include SQL persistence and ownership tests.
- Run npm test from website/ for auth/storage unit tests. tools/auth-storage.mjs
  checks the browser against local auth/SQL services and an imported fixture;
  run one browser at a time. RUN_BROWSER_TESTS=1 enables the backend browser
  integration test for durable generation/projects with offline provider/auth stand-ins.
  No live AI provider is exercised by these tests.
- Run go vet and go test -race from design-service/ for generation, provider transport,
  HTTP jobs/results and all seven housing types, using offline provider stand-ins.
- Keep docs aligned with implemented behavior and report which checks actually ran.
