# AGENT.md

Guidance for an AI agent (or human) working on TerraSim (renamed from SpaceForge on 2026-10-24; the local folder may still be called SpaceForge). This file tracks decisions that are made, decisions that are still open, and the shape of the system so work stays consistent as the project grows.

## What the app does

A user highlights an area on a map (an empty lot, a hillside, any plot of land) and provides design inputs (style, size, rooms, budget, materials, etc.). That input is sent to Gemma, via Google's hosted AI API, to generate a house design suited to that specific site. The system then stores, alongside the design:

- Predicted build cost
- Predicted materials list
- Predicted cost over time (maintenance/appreciation/depreciation projections)

Other users can then browse published designs/listings and contact the builder who generated that design if they want to pursue it — TerraSim is the catalog/lead-gen layer, not a marketplace with transactions built in (at least not yet).

There are two kinds of people who generate designs (decided 2026-10-24, see PRODUCT.md):

- **Builders/developers (primary):** generate designs for land they have the landowner's permission for, and can publish them as listings. Buyers' inquiries go to them.
- **Dreamers:** anyone can generate a house for a plot to look at and share by link, but their designs are private — never published to the catalog and not offered for sale.

## Decisions made so far

This project is **polyglot by design** — each service uses the language suited to its job, not one shared stack:

- **Accounts service:** Go. Handles user accounts/auth as its own service, separate from the main API.
- **API:** Python. The main application API — map/design requests, predictions, inquiries. Framework not yet chosen (FastAPI is the likely pick given async needs for calling the Gemma API, but unconfirmed).
- **Data/analytics:** Python and R. Data processing pipelines and the prediction models (cost, materials, cost-over-time). R is likely for statistical modeling, Python for data wrangling/ML glue — exact split is implementation detail, not fixed yet.
- **Frontend:** HTML/CSS/JavaScript, with **Rive** for interactive/animated UI (e.g. animating the generated house design, map interactions). No JS framework (React/Vue/etc.) has been chosen or implied — don't introduce one without confirming.
- **AI model:** Gemma, accessed through Google's **hosted AI API** (Gemini API / Vertex AI) — not self-hosted. Do not add local model-serving code (e.g. Ollama) unless the user asks.

Decided 2026-10-24 (frontend build):

- **Frontend map: Leaflet + OpenStreetMap** (no API key). Users draw the site outline on it. The map sits behind an adapter so a production provider (Mapbox, Google) can replace it later; see the open decision below.
- **Frontend runs without the backend for now.** It talks to a mock API layer that uses the same request/response shapes the Python API should implement (documented with the frontend). Gemma and the map API are not connected yet.
- **Who gets inquiries:** the builder who generated (and published) the design — not a central TerraSim inbox. How the message is delivered is still open.
- **Publishing needs permission:** a design can only be published as a listing after the builder confirms they have the landowner's permission. Dreamer designs are private, shareable by link only.
- **Units:** a toggle between imperial (sq ft, acres) and metric (m², hectares); prices in USD.
- **Rive assets are generated by code** (`frontend/tools/rive/`), so no Rive editor login is needed. Editor-made `.riv` files may replace them if they keep the same state machine and input names.
- **Motion** (vanilla JS build) for interface transitions; **Playwright** for screenshots and checks (dev only).
- **Visual direction:** "Blueprint + Forge" (chosen by the user), built as an "inspection card" structure: each design's sheet carries a card whose stages are stamped as it goes from site to brief to forge to estimate to published. Product context is in PRODUCT.md; the design system will be recorded in DESIGN.md.
- **Design and review tooling:** see RESOURCES.md (taste-skill, Impeccable, UI UX Pro Max, plus built-in /code-review, /security-review, /simplify).

Because accounts (Go), API (Python), and data/analytics (Python/R) are separate services, expect inter-service communication (REST/gRPC/etc.) rather than in-process calls — don't assume they share a runtime, a process, or a single codebase layout.

## Open decisions (do not assume — ask or flag before building around these)

- **Service boundaries & communication:** How the Go accounts service, Python API, and Python/R data layer talk to each other (REST, gRPC, shared DB, message queue) is not decided.
- **API framework:** Python framework for the API not yet chosen (FastAPI likely, unconfirmed).
- **Production map provider:** The frontend uses Leaflet + OpenStreetMap (decided above). Whether production stays on OSM tiles or moves to a paid provider for imagery/geocoding is open. Candidates discussed:
  - *Mapbox GL JS* (+ Mapbox GL Draw) — best drawing/highlighting UX, good imagery, generous free tier.
  - *Google Maps Platform* — familiar, strong geocoding/street view, drawing tools more DIY.
  - *Leaflet + OpenStreetMap* — free, no API key, good MVP option but less polished imagery.
  - Whichever is picked needs to support: letting a user draw/select an arbitrary polygon or area on the map, and reading back the resulting coordinates/geometry to send to the backend.
- **Data store:** Not chosen (Postgres is a reasonable default given relational data: users, designs, predictions, messages). Needs to support storing structured prediction data (cost, materials list, cost-over-time series) tied to a generated design and its map geometry.
- **Gemma model details:** Exact model variant/endpoint and whether it needs to be multimodal (to reason about terrain/imagery from the map selection, not just text inputs) is unconfirmed. Check actual Google AI API model availability before wiring up calls — don't assume a specific model name is correct without verifying against current API docs.
- **Contact/messaging delivery:** The recipient is decided (the builder who generated the design); the delivery is not. Could be a stored "inquiry" record + email notification, or in-app messaging — scope this with the user before building either. The frontend currently stores inquiries in the mock layer.
- **Auth:** Not decided — needed to tell builders (who can publish and receive inquiries) from dreamers and browsing users, and to record the landowner-permission confirmation against an account.

## Data model sketch (not final — adjust as decisions above are made)

- **Site** — map geometry (polygon/bounds), location metadata.
- **DesignRequest** — a Site + user-provided inputs (style, size, budget, materials, etc.) that was sent to Gemma.
- **Design** — the generated output for a DesignRequest (description, imagery/renderings if any, layout details). Has a visibility: `private` (dreamer, shareable by link) or `published` (builder listing).
- **Builder** — the account that generated a design and receives its inquiries (company name, contact).
- **PermissionAttestation** — the builder's confirmation that the landowner allowed the design to be published (who, when, optional document reference). Required before a Design becomes `published`.
- **Prediction** — cost estimate, materials list, cost-over-time projection, linked to a Design.
- **Inquiry** — a message from a browsing user about a specific published Design, directed to the builder who generated it.

## Working conventions

- This project has no scaffolding yet. When adding the first backend/frontend code, update the README's "Getting started" section with real run instructions in the same change.
- Keep this file in sync with real decisions as they're made — move items from "Open decisions" to "Decisions made so far" rather than letting both sections drift out of date.
- Don't invent API keys, model names, or provider-specific config — leave clearly marked placeholders and flag what needs to be filled in by the user.
